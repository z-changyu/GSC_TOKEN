# 场景重构与端到端数据流（方案 A：文本化多车协调接收端）

> 文档目的：把原"车辆把摄像头画面压成文字描述、发给一个会看图的 RSU 答题"的场景，重构为在 V2X 中可辩护的设定——**RSU 是文本化的多车协调 LLM，车辆发送的是"给协调器看的、任务相关的结构化语义报告"**。本文给出重构后的系统实体、完整端到端数据流，以及每一阶段与现有代码的对应关系。
>
> 配套：本仓库现有实验仍是 ScienceQA 单样本代理（单车、单流、单时隙）。本文描述**目标态**的数据流，并显式标注"已实现 / 待实现"的差距。

---

## 1. 重构动机

### 1.1 原设定的逻辑漏洞
原链路把"车辆把图像压成文字 → 发给 RSU → RSU 答题"当作主线，隐含前提是 **RSU 看不到图、只能靠文字重建场景**。这在 V2X 中站不住：

- **RSU 是路边基础设施，本就带摄像头 / 雷达**。车辆把自己看到的画面用文字复述一遍发给 RSU，等于对一个 RSU 本来能看到、且信息更全的东西做有损压缩再传回，既没省掉"看场景"，又损失信息、还增加两轮推理延迟。
- 论文把接收端定为"纯文本、看不到图"。在 2B 级边缘 VLM（如本仓库 `Qwen3-VL-2B-Instruct`）已可跑图的当下，"发文字替代发图"的带宽理由被大幅削弱。

### 1.2 新设定：一个转变 + 三个不变
- **转变**：接收端从"看不到图的视觉模型"重新定义为 **文本化协调 LLM（shared generative text coordinator）**。它的职责不是"看图答题"，而是**汇总多车的结构化语义报告、融合出全局态势、回答/下发任务**。这样"纯文本接收端"从凑出来的限制变成**系统设计本身**。
- **三个不变（方法核心全部保留）**：
  1. 发射端仍把 `(image, task-intent)` 压缩为语义文本 token；
  2. 仍做逐 token 语用打分（注意力 $A_i$、语义 $S_i$、梯度 $G_i$、耦合 $M_{ij}$）与基于 CSI 的可靠调度；
  3. 信道仍是时变 + 不完美 CSI + 包丢失，接收端只收到（可能残损的）文字。

### 1.3 为什么现在"纯文本接收端"合理
- **下游是文本系统**：RSU/云侧是交通协调 LLM，输入是"多车语义报告 + 任务查询"，输出是"态势/告警/路网指令"。车辆把像素变成结构化文字报告，是对该下游的正确接口，而非权宜。
- **价值来自多车融合**：任何单车都只能看到局部视角；RSU 的价值是**聚合 K 辆车的极小语义报告，形成任何单车都不具备的全局理解**。这正是方案 A 与多车设定（用户系统图里的 K 车 → RSU）的自然合流。

## 2. 系统实体与职责

| 实体 | 角色 | 核心职责 | 对应代码 |
|---|---|---|---|
| **车辆 k（语义发射端）** | `Veh. k: pragmatics-aware semantic transmitter` | 取帧、按任务意图生成语义报告、逐 token 语用打分、可靠感知调度、空中发送 | `src/experiments/scoring.py`、`src/scheduling/` |
| **RSU（共享生成式文本协调器）** | `Road Side Unit: Shared generative receiver` | 摄入 K 路（残损）文字报告、跨车融合、回答任务查询 / 下发告警 | `scripts/run_channel_experiment.py` 的 `receiver`（当前单车，待扩 K 车） |
| **云端（基础模型 + 语义知识）** | `Cloud support: foundation model & semantic knowledge` | 提供并共享 VLM/LLM 权重、标定好的语用权重（语义知识） | `models/`、`pragmatic.weights`、CV 标定（`run_cross_validation.py`） |
| **时变信道** | V2X 空中接口 | 提供不完美 CSI $\hat h_\tau$、可靠容量预算 $C_\tau$、包丢失、实际中断 | `src/channel/`（`build_channel`、`reliable_capacity`、`link`） |

**关键不变式**：车辆 *永不* 把原始图像发给 RSU；RSU *只* 处理文字。图像信息在车端被 VLM "提炼"为语义 token 流，残损部分由文字的语义冗余与跨车融合共同兜底。

## 3. 完整端到端数据流（核心）

### 3.1 总体流图

```
                       ┌──────── 云端：共享 VLM/LLM 权重 + 标定语用权重 ────────┐
                       │   （foundation model & semantic knowledge，周期性下发） │
                       └───────────────────────────────────────────────────────┘
                                        │ 模型/知识同步
        ┌─────────────── 车端 Veh.k（语义发射端，K 路并行）───────────────┐
        │  V1 摄像头取帧 ─▶ V2 VLM 按任务意图生成语义报告                  │
        │                       │                                          │
        │                       ▼                                          │
        │  V3 逐 token 语用打分 A_i,S_i,G_i,M_ij ─▶ 缓存                  │
        │                       │                                          │
        │                       ▼                                          │
        │  V4 可靠感知调度：预算 C_τ(来自 CSI) → 选 token + 保护级        │
        │                       │                                          │
        │              "selected task-relevant semantic tokens"          │
        └───────────────────────┬──────────────────────────────────────────┘
                                │ 空中接口（时变信道 + 不完美 CSI）
                                ▼ 部分 token 被擦除 / 丢包
        ┌─────────────── RSU（共享生成式文本协调器）────────────────────┐
        │  R1 摄入 K 路（残损）文字报告                                   │
        │   R2 跨车融合：聚合 K 份报告 → 全局态势表示                    │
        │    R3 任务回答：协调 LLM 回答查询 / 下发告警                   │
        │  输出：Semantic task output（Q & A / 路网指令）                │
        └───────────────────────────────────────────────────────────────┘
                                │ 反馈回路
                                ▼
        RSU → 车辆：CSI/资源分配(B_k) + 任务意图(查询) → 回到 V1/V4
```

### 3.2 阶段分解

#### V1 — 感知与任务意图（Sensing & task intent）
- **输入**：车辆摄像头帧 `image`；来自 RSU/协调器的任务查询 `query`（如"前方车道是否被阻断？"+ 候选）。
- **处理**：帧作为本地观测；查询作为 *task intent* 注入发射端 VLM 的提示，使后续描述"任务相关"。
- **输出**：`(image, _request)`，其中 `_request` 含问题+选项（即 `TRANSMITTER_REQUEST` 模板）。
- **代码**：`data/processed/...jsonl` 的 `image` 字段；`_request` 经 `build_transmitter_messages` 进入 `generate_prompt`。
- **状态**：当前实验中"查询来自数据集"与"查询来自 RSU"逻辑等价——车辆侧始终持有查询即可条件化。

#### V2 — 语用生成（Pragmatic generation → 语义报告）
- **输入**：`(image, _request)`。
- **处理**：VLM 将图像 + 任务意图转为紧凑文字报告 `semantic_prompt`（即"给文本协调器的语义报告"，不暗示答案、只描述判别性证据）。
- **输出**：`semantic_prompt: str`。
- **代码**：`scoring.py:127` `PragmaticScorer.generate_prompt`；系统提示见 `prompts.py:6`（`SYSTEM_PROMPT` 写明"为看不到图的接收端写描述"，此处即协调器）。
- **方程**：对应论文语义描述生成 $P=\{w_i\}_{i=1}^N$。

#### V3 — 逐 token 语用打分（Token-level pragmatic scoring）
- **输入**：`semantic_prompt` 与 `(image, question, choices)`。
- **处理**：构造 `[user: I,Q][assistant: P][user: request]`，teacher-forcing 真值答案，读取 prompt 片段的嵌入梯度与自注意力，按 token 计算四种效用分量。
- **输出**：每 token 的 `(A_i, S_i, G_i, M_{ij})` 与 `token_ids`，写入评分缓存。
- **代码**：`scoring.py:148` `PragmaticScorer.score` → 落盘 `outputs/cache/scienceqa_scores_coupling.jsonl`；分量由 `pragmatic/`（attention/semantic/gradient/coupling）计算；合并见 `combine_scores`（权重 `[0.25,0.0,0.75]`）。
- **方程**：$A_i$（式 1）、$S_i$（式 2）、$G_i=\|\partial\mathcal L/\partial e_i\|_2$（式 3）、$M_{ij}$（式 5）；基础效用 $u'_i$ 与上下文效用 $u_i=u'_i+\beta\sum_{j\ne i}M_{ij}u'_j$（式 4、6）。

#### V4 — 可靠感知调度（Reliability-aware scheduling）
- **输入**：每 token 效用 $u_i$；来自信道的预算 $C_\tau$ 与不完美 CSI $\hat h_\tau$；保护码本。
- **处理**：Algorithm 1（Lagrangian LP → certified rounding → coupling-aware local refinement）在预算内选 token 并分配保护级 $\{r_H,r_M,r_L\}$。
- **输出**：`level[i]`（选中/保护级）。
- **代码**：`run_channel_experiment.py:157` `select_level(...)`；预算 `budget = T_s·B·c_eps(h_hat)`（式 6，可靠容量）见 `reliable_spectral_efficiency`；解码概率 `decoding_probability`；`state.h_hat` 即不完美 CSI。
- **多车扩展（目标态）**：RSU 按 $B_k = B\,[p_k|\hat h_k|]/\sum_j[p_j|\hat h_j|]$ 分配每车带宽（论文多终端式 43–50），使 K 路语义流争用信道时按效用密度公平分配。

#### C — 信道传输与擦除（Channel transmission）
- **输入**：选中的 `token_ids`（属于 `semantic_prompt` 文本）。
- **处理**：按保护级编码 → 实际信道（realized rate + 包丢失）决定 token 存活；被擦除 token 不进入 RSU。
- **输出**：`received_text = decode(kept token_ids)`（可能残缺）。
- **代码**：`run_channel_experiment.py:165` 选 token、`run_channel_experiment.py:175` `channel.transmit(transmitter_tokenizer.decode(kept))`。
- **说明**：**传输的是文字 token，不是图像、不是问题文本本身**（早期 pilot 的 bug 已修）。

#### R1 — 接收端摄入（Ingest）
- **输入**：K 路 `received_text`（当前实验为单车单路）。
- **处理**：用发射端 tokenizer 解出的文字，拼接待回答请求，构造接收端输入。
- **代码**：`run_channel_experiment.py:182` `apply_chat_template([{"role":"user","content":f"{ANSWER_REQUEST}\n\n{received}"}])`；`receiver`（当前 `Qwen3-1.7B`，纯文本）。
- **状态**：当前 `receiver` 是文本 LLM，与"文本协调器"设定一致；若需 RSU 也看图则走形态 A 的变体（接收端 VLM），但那会削弱"省带宽"主线，**非默认**。

#### R2 — 跨车融合（Cross-vehicle fusion，目标态 / 待实现）
- **输入**：K 路 `received_text_k`（各车可能残缺）。
- **处理**：协调 LLM 将 K 份报告在上下文内拼接/对齐，融合出单一全局态势表示；残缺报告由其余车辆与文字语义冗余补位。
- **输出**：融合后的态势上下文（喂给 R3）。
- **设计（建议）**：接收端输入 = `ANSWER_REQUEST + [received_text_1 ‖ received_text_2 ‖ … ‖ received_text_K]`；协调 LLM 基于全部报告作答。
- **状态**：**当前代码未实现**（单车单流）。这是方案 A 真正成立、也最贴合用户系统图的关键缺口。

#### R3 — 任务回答（Task answer）
- **输入**：融合态势 + 查询。
- **处理**：协调 LLM 生成答案；解析为选项/告警。
- **输出**：`Semantic task output`（如用户图例："Is the lane ahead blocked? — Yes. Fallen cargo blocks the right lane."）。
- **代码**：`run_channel_experiment.py:187` `receiver.generate` → `run_channel_experiment.py:194` `canonical_prediction` → `exact_match` 计 accuracy。

#### F — 反馈回路（Feedback loop）
- **CSI/资源反馈**：RSU 估计/下发不完美 CSI $\hat h_\tau$ 与每车带宽 $B_k$ → 车端 V4 据此调度（已在 `state.h_hat` / `budget` 体现）。
- **任务意图反馈**：RSU/任务方将查询下发给相关车辆 → 车端 V1 作为 task intent 条件化生成。
- **状态**：CSI 反馈在信道模块已实现；"查询由 RSU 动态下发"在当前实验用数据集查询等价替代。

## 5. 关键设计决策与可辩护性

1. **"纯文本接收端"从限制变为设计**：RSU 是文本协调 LLM，输入天然是文字报告；因此"只传文字、不传图"是接口正确，而非信息损失。
2. **单车贡献极小化**：每辆车只发"任务相关、判别性"的语义报告（V3 效用打分保证），K 车聚合才是价值来源——这正对应论文"语用 token 选择"的贡献点。
3. **方法-载荷正交**：语用打分 + 可靠调度的方法论不依赖载荷是图还是文字；方案 A 只是把"载荷为何是文字"讲圆，方法本体不变。
4. **鲁棒性由两层兜底**：单报告内文字语义冗余（V2 描述而非索引）+ 跨车冗余（R2 融合），使信道擦除后仍能作答。

## 6. 当前实现 vs 目标场景的差距

| 维度 | 目标态（方案 A） | 当前实现 | 缺口 |
|---|---|---|---|
| 接收端角色 | 文本化多车协调 LLM | 单车文本 LLM 答题 | R2 融合未实现 |
| 车辆数 | K 路并行 + 带宽分配 | 单样本独立流 | 多终端调度未接入实验 |
| 查询来源 | RSU 动态下发 | 数据集固定查询 | 等价替代，待显式 |
| 连续性 | 视频流 / 持续任务 | 单图一次性 VQA | 时间相关性未建模 |
| 云端更新 | 周期性权重/知识下发 | 静态本地模型 | 仅标定权重写入 config |
| 图像是否在车端提炼 | 是（RSU 从不看图） | 是 | 一致 ✅ |

**优先补强**：R2（跨车融合）+ 多终端带宽分配接入实验，是让方案 A 在论文中真正成立的最短路径。

## 7. 论文叙述建议（brief）

- **§II 系统模型**：删去"RSU 看不到图故需文字重建"的隐含前提，改为"RSU 是文本化协调器，聚合多车语义报告"；明确 CSI 反馈与任务意图下发两条回路。
- **§III/§IV**：方法描述基本不变；强调效用打分服务于"每车极小报告 + 跨车融合"的语义通信本质。
- **§VI 实验**：在单样本代理之外，必备 K 车融合小仿真，否则"协调器"设定无支撑；明确标注 ScienceQA 是单图代理。
- **上界**：将"多模态模型直接看图"作为**独立上界**列出（测"若接收端有图"的精度），与"纯文本协调器"主线区分，避免被审稿人质疑"为何不直接传图"。
